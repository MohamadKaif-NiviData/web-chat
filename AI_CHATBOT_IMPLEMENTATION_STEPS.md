# AI Chatbot (Ollama) — Backend + Frontend Implementation Steps

Follow these in order — each step builds on the last and should leave the
app in a working (if incomplete) state. For the design rationale, see
`AI_CHATBOT_PLAN.md`; for acceptance criteria, see
`AI_CHATBOT_USER_STORIES.md`.

`docker-compose.yml`'s `ollama-chat-app` service is already in place (added
and fixed earlier) — that's why it isn't listed as a step below. This doc
picks up from there.

---

## 0. One-time manual setup (not code)

**Why**: same spirit as the push notifications feature's VAPID keys and the
S3 bucket — a resource created by hand once, not generated by app code on
every startup.

**Steps**:
1. Bring the stack up so the `ollama-chat-app` container exists:
   ```bash
   docker compose up --build -d
   ```
2. Pull the model once, inside that container:
   ```bash
   docker compose exec ollama-chat-app ollama pull llama3
   ```
3. This downloads several GB into the `ollama_data` named volume, so it
   survives `docker compose down` (but NOT `docker compose down -v`) and
   never needs re-pulling on a normal restart.
4. **Resource gotcha**: `llama3` (8B) wants roughly 8GB RAM to run at a
   usable speed on CPU-only inference (no GPU passthrough from Docker
   Desktop by default on macOS). If responses take minutes or the container
   swaps heavily, that's almost certainly why — not a bug in the code below.
   A quantized variant (e.g. `llama3:8b-instruct-q4_0`) or a smaller model
   (e.g. `phi3`) is a reasonable fallback if this machine struggles.
5. Sanity-check it works before writing any backend code, same "exercise
   the engine before any app code exists" approach used for S3 in Step 12:
   ```bash
   curl http://localhost:11434/api/chat -d '{
     "model": "llama3",
     "messages": [{"role": "user", "content": "Say hello in one sentence."}],
     "stream": false
   }'
   ```
   You should get back a real JSON response with a `message.content` field
   containing actual model output. If this hangs or errors, fix it here —
   nothing past this point will work until it does.

## 1. `.env` (modify)

**Steps**:
1. Add `OLLAMA_BASE_URL=http://ollama-chat-app:11434` — note the hostname is
   the Compose **service name** (`ollama-chat-app`), not `localhost`; the
   backend reaches it over the Compose network, the same way it reaches
   `postgres-chat-app`/`redis-chat-app` by service name rather than
   `localhost`.

**Steps**:
1. Add `httpx` (pin a version) — the async-native HTTP client for calling
   Ollama's REST API, consistent with this backend's async-everywhere
   style (vs. wrapping a sync library in `asyncio.to_thread`, the way

## 4. `backend/app/schemas/ai_chat.py` (new)

**Why**: shaping the request/response as Ollama's own `/api/chat` shape
(`role`/`content` messages) means the frontend's local state can be
forwarded almost unchanged — same "mirror the external API's shape"
reasoning as `PushSubscriptionRequest` mirroring the browser's
`PushSubscription.toJSON()`.

**Steps**:
1. `class ChatMessage(BaseModel)`: `role: str`, `content: str` — `role` will
   be `"user"` or `"assistant"`.
2. `class AiChatRequest(BaseModel)`: `messages: list[ChatMessage]` — the
   **entire** conversation so far, since nothing is persisted server-side
   (see `AI_CHATBOT_PLAN.md`'s scope decisions).
3. `class AiChatResponse(BaseModel)`: `reply: str`.

---

## 5. `backend/app/services/ollama.py` (new)

**Why**: one shared helper the route calls, instead of inlining the HTTP
call directly in the route handler — same reasoning as `services/push.py`
being separate from `api/routes/push.py`.

**Steps**:
1. `async def send_chat_message(messages: list[dict]) -> str`.
2. Use an `httpx.AsyncClient` with a generous timeout (model inference on
   CPU can take tens of seconds — don't reuse `httpx`'s short default):
   ```python
   async with httpx.AsyncClient(timeout=120.0) as client:
       response = await client.post(
           f"{settings.ollama_base_url}/api/chat",
           json={"model": "llama3", "messages": messages, "stream": False},
       )
       response.raise_for_status()
       data = response.json()
       return data["message"]["content"]
   ```
3. Let `httpx.HTTPError` (covers connection failures, timeouts, and
   `raise_for_status()`'s non-2xx errors) propagate up uncaught — the route
   in Step 6 is what turns it into a clean `502`, not this function. Keeping
   the translation at the route layer (not here) matches how `push.py`'s
   service layer raises/handles `WebPushException` itself, while this one
   has a simpler single-call shape with no per-item loop to protect.

---

## 6. `backend/app/api/routes/ai_chat.py` (new)

**Steps for `POST /ai/chat`** (body: `AiChatRequest`, behind
`get_current_user`):
1. Convert `payload.messages` into the plain `list[dict]` shape
   `send_chat_message` expects: `[m.model_dump() for m in payload.messages]`.
2. Call `await send_chat_message(messages)` inside a
   `try`/`except httpx.HTTPError`.
3. On success, return `AiChatResponse(reply=reply_text)`.
4. On `httpx.HTTPError`, raise `HTTPException(status_code=502, detail="AI
   service is currently unavailable")` — never let an unreachable/down
   Ollama container surface as an unhandled traceback (Story 7).
5. No conversation/participant authorization check needed here, unlike
   every route in `conversations.py`/`chat.py` — this endpoint doesn't touch
   `Conversation`/`Participant` rows at all; `get_current_user` alone is the
   full authorization requirement (Story 6).

## 8. `frontend/app/ai-chat/page.tsx` (new)

**Why**: a dedicated page outside `app/chat/`, since this is explicitly NOT
part of the conversation/participant system (Story 1).

**Steps**:
1. `"use client"` component. On mount, same auth guard as
   `app/chat/page.tsx`: if `!isAuthenticated()`, `router.replace("/login")`.
2. Local state only — nothing persisted:
   - `messages: {role: "user" | "assistant", content: string}[]`
   - `input: string` (the textbox)
   - `sending: boolean` (drives the "thinking" indicator and disables input —
     Story 3)
   - `error: string | null`
3. `handleSend`:
   - Build `const nextMessages = [...messages, {role: "user", content: input}]`.
   - `setMessages(nextMessages)`, clear the input, `setSending(true)`,
     `setError(null)`.
   - `const { reply } = await apiJson("/ai/chat", { method: "POST", body:
     JSON.stringify({ messages: nextMessages }) })` — note the **entire**
     `nextMessages` array is sent, not just the latest message (Story 4).
   - On success: `setMessages([...nextMessages, {role: "assistant", content:
     reply}])`.
   - On failure (the `502` from Step 6, or a network error): `setError(...)`
     with a readable message — never a raw stack trace (Story 7).
   - `finally`: `setSending(false)`.
4. Disable the send button/input while `sending` is `true` (Story 3) — this
   is the simplest way to prevent a second request racing the first given
   there's no request queue or message-ordering logic here, unlike
   `chat.py`'s WebSocket loop.
5. Render: a simple scrollable message list (map over `messages`, style
   `role === "user"` vs `"assistant"` differently — reuse `MessageList`'s
   visual conventions if convenient, but don't reuse its actual component,
   since it's built around `Message`/`Attachment`/read-receipt types this
   feature doesn't have), a text input, a send button, and a "← Back" link
   to `/chat` (same pattern as `app/chat/[conversationId]/page.tsx`).
6. Deliberately no `useEffect`-based history fetch — there is nothing to
   fetch. A fresh page load always starts with `messages: []` (Story 5).

## Verification checklist

Work through these as you complete each step above — don't wait until the
end to test everything at once.

- **After Step 0**: the `curl` sanity check against Ollama directly returns
  real model output. Don't proceed until this works — every later failure
  will otherwise be ambiguous (is it your code, or is Ollama not ready?).
- **After Step 7**: `docker compose up --build` starts cleanly, no import
  errors.
- **Happy path**: `POST /ai/chat` as an authenticated user with a real
  message → a real `llama3`-generated reply, not an echo, not an error
  (Story 2).
- **Auth check**: `POST /ai/chat` with no/invalid token → `401` — confirm
  this happens before any call to Ollama (check backend logs; there should
  be no outbound request logged) (Story 6).
- **Down-service check**: stop `ollama-chat-app`
  (`docker compose stop ollama-chat-app`), then hit `/ai/chat` again →
  clean `502`, no unhandled traceback in backend logs (Story 7). Restart it
  afterward (`docker compose start ollama-chat-app`).
- **Context check**: in the browser, send a message, wait for the reply,
  then send a follow-up that only makes sense with that context (e.g. "what
  did I just ask you?") → confirm the reply shows the model actually has
  the earlier message (Story 4) — this also proves the frontend is resending
  the full `messages` array correctly, not just the latest one.
- **Thinking state**: confirm the UI visibly shows a waiting/thinking state
  and the input is disabled while a request is in flight (Story 3).
- **Ephemeral check**: refresh the page mid-conversation → chat box is
  empty again (Story 5) — this is expected, not a regression.
- **Isolation check**: confirm the AI conversation never appears in the
  regular chat list (`GET /conversations/`) and no new row appears in
  `conversations`/`participants`/`messages` after using it.
